01 — 目标

钱包是种子的新派生分支，而非外挂的密钥

把 Auth Box 从「零知识金库 + AI 代理密钥中枢（agent broker）」升级为同时也是一个自托管多币种加密钱包，先支持比特币与以太坊 / EVM（Ethereum Virtual Machine，以太坊虚拟机）。核心约束：不引入任何新的托管风险，不改变既有的零知识安全姿态。

02 — 核心洞察

种子本就是钱包种子

Auth Box 已经在保护一个 BIP-39 的 24 词助记词（packages/crypto/src/seed.ts）。其 mnemonicToSeed 完全符合 BIP-39 规范（PBKDF2-HMAC-SHA512，盐 "mnemonic"，2048 次迭代，64 字节输出）。因此用户手里已有的这串短语本身就是一个标准钱包种子 —— 加密钱包不是一个外挂的新秘密，而是用户已经掌控的那颗种子上的一条新派生分支。

03 — 密钥树

一个种子，两棵密码学独立的 HD 树

树HMAC 密钥派生方式用途互操作
Auth Box 内部树"authbox seed"自定义、仅硬化（deriveKey）金库 / 同步 / 代理 / 密码密钥无（刻意）
钱包树"Bitcoin seed"标准 BIP-32BTC / ETH 密钥完整（BIP-44/84）

两棵树虽共享同一颗种子，却因 HMAC 密钥不同而密码学独立（密钥材料完全不相交）。内部树保持自定义结构（其密钥是用于 AES/HKDF 的对称秘密，无需互操作）；钱包树保持标准，使同一串助记词能在 Electrum / MetaMask / Ledger 中恢复出完全相同的地址。「不锁定」是硬性要求 —— 这正是自托管的全部价值所在。

05 — 安全模型

自托管 + watch-only 服务器

金库的零知识属性原样延伸到钱包：

私钥永不离开设备

私钥在客户端从种子派生，签名在本地完成，服务端从不接触密钥材料。

服务器只读观察

服务端只持久化账户级 xpub（扩展公钥）与派生地址 —— 够扫描余额与历史，永远不够花费。

服务器无法自行动用资金

与金库同一信任边界：服务端被完全攻陷只泄露公开地址与余额（隐私损失），而非托管权。但它仍能让用户批准的那笔发送变差，见下文。

服务端只转发，不签名。自 Phase 5b 起，web 端把已经签好的原始交易交给 POST /api/v1/wallet/broadcast，由它原样转发到固定的公共节点（见 services/api/internal/service/broadcast_provider.go 中 BroadcastProvider 的注释）。即使中继被攻陷，它最多能扣下或拖延一笔广播，却改不了金额、收款方或手续费 —— 任何改动都会让签名失效。中继本身不区分主网与测试网，主网的那道闸门放在客户端（services/api/cmd/api/main.go 路由上方注释，L250-252）。

服务器被攻陷后仍能做什么。它签不了名，但在 web 端，客户端签名所依据的数据是它给的，签好的结果也经它转发：

  • 抬高手续费。BTC 费率档位来自 GET /wallet/btc/fees；buildBtcTransaction 会拒绝高于 MAX_BTC_FEE_RATE_SAT_PER_VB（5000 sat/vB，packages/crypto/src/wallet-tx.ts）的费率，所以损失有上限，但不是零。ETH 的 gas 来自 GET /wallet/eth/gas，wallet-send.ts 和 wallet-tx.ts 都没有设上限（micro-eth-signer 自己有没有限制，本文未核实）。真正的把关是复核页在确认之前列出的手续费与合计（§8.3）。
  • 给出错误的 UTXO 或 nonce。P2WPKH 签名会把每个输入的金额签进去，金额造假只会得到一笔被节点拒收的交易；ETH nonce 错了，交易会被拒或卡住。这属于拒绝服务，而不是盗币。
  • 扣下广播，或报一个假 txid。对话框显示的是中继返回的 txid，照单全收。
  • 读取 xpub。它能推出该账户的全部地址，包括还没用过的。

在 web 端，助记词是敲进网页代码里的，而这份代码由 web 主机下发。界面上那句「your seed never leaves the browser」（apps/web/app/(vault)/wallet/page.tsx L1230）对当前发布的代码成立；可一旦 web 主机或构建流程被攻陷，就可能换上一份截取助记词的代码 —— 凡是浏览器里运行的钱包都有这个问题。iOS 没有这道代码下发的环节，但它直接信任 mempool.space / publicnode 提供的同类交易准备数据（§10）。

威胁模型说明：从保护金库的同一颗种子派生钱包密钥，意味着种子一旦泄露，金库与资金同失。这是「单种子」模型的固有性质（与每一个硬件钱包完全相同），并未改变既有姿态 —— 种子本来就是最要紧的资产，因为金库密钥早已由它派生。

手搓 secp256k1 的子密钥派生正是钱包染上 CVE 的地方（常量时间标量加、IL ≥ n 重试）。两个平台都把曲线运算交给已审计的 libsecp256k1 这一系；只有 BIP-39 短语逻辑与哈希/编码原语（纯位运算）是手写的，并对齐向量。

iOS 值得记录的坑：libsecp256k1 的静态 context 缺少 ecmult_gen 表，导致 pubkey_create 直接 abort —— 封装必须用 secp256k1_context_create(SECP256K1_CONTEXT_NONE) 创建 context；静态单例标注 nonisolated(unsafe) 以满足 Swift 6 并发。
07 — 跨平台一致性

打通契约：同一种子 → 同一地址

Web 与 iOS 从同一颗种子派生，必须产出完全相同的地址。Swift 栈（apps/ios/AuthBoxCrypto/Sources/AuthBoxCrypto/Wallet.swift）逐步镜像 TypeScript 栈（packages/crypto/src/wallet.ts）：「Bitcoin seed」主密钥 → 硬化 + 非硬化 CKDpriv（childPriv = (IL + parentPriv) mod n，其中 IL = HMAC-SHA512(chainCode, 压缩父公钥 ‖ index)）→ BIP-84 P2WPKH / BIP-44 P2PKH / ETH EIP-55 → 账户 xpub。

一致性以公开的 all-zeros 助记词（abandon … about）的共享外部锚点来证明，两个平台逐字节产出：

币种路径地址

BTC 传统m/44'/0'/0'/0/01LqBGSKuX5yYUonjxT5qGfpUsXKYYWeabA

08 — 交易签名与发送流程（Phase 5a + 5c · web）

本地签名，确认后才广播

8.1 签名层（packages/crypto/src/wallet-tx.ts）

在客户端完成构建与签名，这个模块本身从不联网：

  • buildBtcTransaction —— 用 @scure/btc-signer 的 selectUTXO 选币 + 找零，P2WPKH 用 witnessUtxo / P2PKH 用 nonWitnessUtxo。它先为每一个候选 UTXO 都派生好密钥，但只给 selectUTXO 真正选中的输入逐个签名（signIdx）；无论是否被选中，所有派生出的密钥都会在 finally 中 fill(0) 清零。返回 { hex, txid, fee, vsize }；txid 为大端展示序。费率低于 1 或高于 MAX_BTC_FEE_RATE_SAT_PER_VB（5000 sat/vB）会被拒绝。传统 P2PKH 输入单凭 outpoint 签不了：调用方必须提供前一笔交易（prevTxHex → nonWitnessUtxo），否则函数直接报错。
  • buildEthTransaction —— 用 micro-eth-signer 的 Transaction.prepare({type:'eip1559'}).signBy(priv)。chainId 与密钥所属网络对不上（主网 ⇔ chain 1）时直接拒绝，测试网路径的密钥签不了主网交易，反之亦然。恢复出的 sender 必须等于独立派生的地址（不一致就直接报错，绝不交回一笔动用了意外密钥的交易）；私钥在 finally 中清零。
记录的发现：micro-eth-signer 的 ECDSA 是对冲式（hedged）签名（在 RFC6979 nonce 上额外加熵 → 每次签名不同，但都有效、都能恢复出同一个 sender），而 @scure/btc-signer 是确定性签名。所以测试按币种断言各自该守的不变量：ETH 看「有效 + sender 可恢复」，BTC 看「确定性」。密钥本地派生、只用一次、用完清零。

8.2 资金关键的发送辅助函数（packages/crypto/src/wallet-send.ts）

全部是纯函数（不联网、不读时钟、不用随机数），并从 packages/crypto/src/index.ts 导出。这样钱包里代价最高的两类错误 —— 小数位算错、手续费设错 —— 可以脱离 React 单独用测试钉死：

  • parseAmount(input, decimals) —— 十进制字符串直接转成最小单位的 bigint，全程不经过浮点数；遇到超出精度的小数位、科学计数法、负数或零一律报错，而不是悄悄截断。
  • selectBtcFeeRate(fees, tier) —— 按档位取 sat/vB 费率，下限不低于 minimumFee，也不低于 1。
  • deriveEthFeeParams(gasPrice, priority) —— EIP-1559 的费用上限取 gasPrice + priority，保证 maxFeePerGas ≥ maxPriorityFeePerGas 恒成立。
  • ethChainId(network) —— 主网 1，测试网（Sepolia）11155111。

8.3 发送对话框（apps/web/app/(vault)/wallet/page.tsx）

分两步走，第二步是整个流程里唯一真正改变链上状态的动作：

  • 复核（handleSendReview）—— 校验助记词，调用 parseAmount，再用 assertSeedMatchesAccount 确认这串助记词派生出的 xpub 与所选账户一致，不一致就拒绝。BTC：取费率档位，列出账户的全部地址，逐个地址查 UTXO，并给每个 UTXO 打上该地址的 change/index 标签（UTXO 本身不带派生路径），再派生一个新的找零地址（序号取已登记的 change:1 地址中最大序号再加一），然后签名。ETH：并行取 nonce 和 gas，算出费用参数，从账户的 change:0/index:0 地址签一笔 21000 gas 的普通转账。对话框在发出任何东西之前就把手续费与合计摆出来（之所以先签后看，是因为 BTC 的手续费取决于签名后才知道的 vsize）：BTC 显示的是签好交易的准确手续费；ETH 显示的是上限 21000 × maxFeePerGas，实际支付不会超过这个数。助记词在 finally 中从 React 状态里清掉，但这只是丢掉引用：JS 字符串本身和处理函数里派生出的 64 字节种子都没有被清零，抹除只能算尽力而为，交给垃圾回收。对话框从不传 prevTxHex，UTXO 接口也不返回它，所以从传统（P2PKH）BTC 账户发送 —— 添加账户表单里提供这个选项（L927）—— 会在签名时报错：web 发送只适用于原生隔离见证 BTC 和 ETH（据代码推断，未实际运行）。
  • 确认（handleSendConfirm）—— 先把 BTC 找零地址登记到 API（这样找零仍算进应用内余额；万一随后广播失败，多登记一个未用地址也无害），再调用 walletApi.broadcast，显示 txid 和区块浏览器链接（explorerTxUrl：按网络指向 mempool.space 或 Etherscan），最后刷新地址与余额。
主网人工闸门（HITL）：主网交易在复核页会出现一个红色勾选框（「This is a mainnet transaction moving real funds. It is irreversible. I have verified the recipient and amount.」），不勾选，「Confirm & send」按钮就保持 disabled；测试网没有这个勾选框，只在发送表单的标签行里写着「Safe testnet -- no real value」。需要说明的是：这道闸门只靠按钮的禁用状态把守，handleSendConfirm 和服务端中继都不会再查一遍（见 §12「待决事项」）。

找零地址登记和「助记词必须属于该账户」这两项检查，比对话框本身晚落地：对话框随提交 be6ede8（2026-06-17）上线，这两项来自提交 01583fb（2026-11-27）。

09 — 服务端

Go API：只读观察、交易准备读取、广播中继

所有钱包路由都挂在 /api/v1 下，位于套用了 auth.Middleware(authService) 和受保护限流器的那个路由组里（services/api/cmd/api/main.go L184-197，钱包路由 L253-270）。处理器在 services/api/internal/handler/wallet_handler.go，服务在 services/api/internal/service/。API 只存 xpub、地址和缓存余额；不持有任何密钥材料，也无法签名。

  • balance_provider.go —— 查余额。
  • txprep_provider.go（TxPrepProvider）—— BtcUTXOs（mempool /address/{a}/utxo，金额以十进制字符串返回）；BtcFeeRates（/v1/fees/recommended，非主网请求失败时改查主网 —— 主网费率对没有实际价值的测试网交易来说是安全的高估，见提交 8f5193f）；EthNonce（eth_getTransactionCount … "pending" 转十进制）；EthGas（eth_gasPrice + eth_maxPriorityFeePerGas，后者不可用时退回 1.5 gwei）。地址先过 btcAddrRe / ethAddrRe 格式检查；BTC 地址经路径转义拼进 UTXO URL，ETH 地址放在 JSON-RPC 请求体里。
  • broadcast_provider.go（BroadcastProvider）—— BTC：以纯 hex 文本 POST {base}/tx，要求返回 64 位 hex 的 txid；ETH：调用 eth_sendRawTransaction，要求返回带 0x 的 32 字节哈希。IsWellFormedRawTxHex 限定载荷形态（可带 0x、偶数长度 hex、20 至 200 000 个 hex 字符），provider 内部还会再校验一遍。

校验与错误：不在词表内的 coin/network、格式不对的 rawTxHex，在任何外发请求之前就返回 400；交易准备接口缺 address 也返回 400，但如果带了地址而格式不对，会在 provider 的格式检查处失败，和其他交易准备的上游失败一样返回 502。广播失败返回 502，正文是 provider 的错误信息：节点给了拒绝原因就是那条原因，否则是网络或状态码错误（wallet_handler.go 的 Broadcast）。广播请求不带 network 时会发往主网（broadcast_provider.go 的 Broadcast，L88-89）；web 客户端每次都会带上它。广播不会写入审计链：处理函数只在失败时记一条 slog.Warn（含用户、币种、网络和错误）。web 端调用这些接口的客户端是 packages/api-client/src/client.ts 中的 walletApi，由 apps/web/lib/api.ts 实例化。

10 — iOS 集成

local-first，无服务端往返

iOS app 是 local-first（本地优先） 的，不使用 Go 钱包 API。APIClient 在 iOS 上是死代码（未接入登录流；金库本就是 Keychain seed + SwiftData，完全在设备上）。仅为取一个余额而重建一套缺席的认证流是净负收益，因此 iOS 钱包客户端派生，并直连同一组公共索引器（WalletBalanceService：mempool.space / publicnode）。这比 web 路径的零知识更强 —— 地址列表从不离开设备到自家服务器 —— 且与 local-first 金库一致。

持久化（WalletAccountStore，UserDefaults）只存公开账户描述符（币种 / 网络 / 脚本类型 / 索引 / 标签）—— 无密钥、无地址。收款地址在金库解锁时由内存中的种子实时重新派生，于是静态落盘的足迹不含任何敏感物。

iOS 的发送同样坚持本地优先。WalletTxPrepService.swift 直接向 Go provider 所用的同一组固定主机查询 UTXO、费率档位、nonce 和 gas，并自己完成广播（broadcastBtc → mempool.space POST /tx，broadcastEth → publicnode JSON-RPC），不经过 Go 中继。签名在 apps/ios/AuthBoxCrypto/Sources/AuthBoxCrypto/WalletTx.swift 中原生完成（buildBtcTransaction：P2WPKH / BIP-143；buildEthTransaction：EIP-1559，配合 RLP.swift），另有 WalletTx.isValidRecipient 负责输入时的收款地址校验。原生签名器不设手续费上限：BTC 只要求不低于 1 sat/vB（没有对应 web 端 MAX_BTC_FEE_RATE_SAT_PER_VB 的限制），ETH 则照单使用传入的 gas 参数，所以复核页上的「Network fee」一行就是防范错误费率数据的那道关。SendWalletView.swift 是「复核 → 确认」两步的弹出面板；主网下，必须先打开「I confirm sending real … on mainnet.」开关，确认按钮才可用。DEBUG 视觉验收入口 --send-demo-broadcast（在 App/ContentView.swift 读取）可以自动确认，但 SendWalletView 只在 isTestnet 为真时才会触发它。
